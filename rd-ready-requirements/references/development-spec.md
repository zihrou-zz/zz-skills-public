# 開發需求書寫作規格

產出或更新交付 RD 的需求書時讀取本檔。

## 讀者與完成效果

主要讀者是第一次接觸需求的 RD，次要讀者是 QA、設計與需求方。文件讀完後，RD 應能：

- 用自己的話重述使用者從開始到完成的行為。
- 說明系統在哪些節點判斷什麼，以及結果如何影響使用者。
- 列出主要狀態、規則、資料依賴、失敗策略與權限。
- 切出可估工的端到端開發項目。
- 從文件直接找到驗收方式，不需回頭翻聊天紀錄。
- 把剩餘問題限定在技術設計，而非產品到底要什麼。

## 預設交付物

檔名為 `rd-development-spec.md`。文件開頭放：

- 功能／專案名稱、版本與日期。
- Owner、決策人與主要讀者。
- Readiness：`DRAFT / PRODUCT_READY / RD_READY`。
- 一句話目標與本次範圍。
- 若非 RD Ready：阻塞項、決策人與何時再確認。

## 需求書結構

依需求相關性增減細節，但不得省略會改變實作結果的內容。

### 1. 為什麼做

說明目標使用者、現在怎麼做、痛點、做錯或不做的代價、期望結果、成功指標及其取得方式。避免空泛 Persona 和無法量測的口號。

### 2. 本次範圍

分成 `In scope / Later / Out of scope`，寫出本次 appetite、時程或其他硬限制。用結果描述範圍，不用頁面數量代替範圍。

### 3. 使用者如何使用

這是需求書的主體，必須排在系統細節之前。每條端到端情境寫明：

- 角色、觸發、入口、當時脈絡與目標。
- 依時間或操作順序列出使用者行為。
- 每一步系統顯示、處理或回饋什麼。
- 使用者決定點、系統判斷點及分支結果。
- 成功、放棄、失敗、中斷、返回、重試與角色交接。
- 頻率、資料量、時限、裝置或實際操作環境。

複雜流程應附 UI Flow、sequence、state diagram 或 prototype；簡單流程以編號步驟即可。圖不能取代文字規則，文字也不能讓 RD 自行想像畫面上的關鍵資訊。

### 4. 畫面與互動需求

只有確實存在 UI 時才寫。依使用者行為節點描述：

- 入口與可見條件。
- 使用者需要看見的資訊與資訊層級。
- 可執行動作、disable／阻擋條件。
- loading、empty、success、error、partial success。
- 重新整理、返回、重開、中斷續作與重複操作。
- 需要固定的文案、排序、數量或平台差異。

不要替設計師決定無關緊要的像素；若畫面呈現會改變判斷、風險或驗收，就必須寫清楚。

### 5. 業務規則、狀態與權限

規則寫成條件 → 結果，標示適用範圍與優先序。狀態需有進入條件、允許動作、離開條件、觸發者、可逆性與終止狀態。權限同時寫「看得到什麼」與「做得到什麼」，不可只靠前端隱藏。

規則複雜時用決策表；狀態複雜時用狀態圖。每一條重要規則至少附一個具體例子。

### 6. 資料與外部依賴

寫出業務需要的資料、來源、權威來源、新鮮度、識別方式、缺值含義及資料失敗政策。已有系統或程式碼時，引用已驗證的真實欄位與限制；未知技術 schema 不要由需求方虛構。

外部 API、人工流程、排程、migration、歷史資料、重跑、冪等、併發、稽核與監控，只在相關時展開。每個依賴標 owner 和未就緒時的影響。

### 7. 例外與失敗處理

至少覆蓋與本需求相關的：資料源失敗、部分成功、重複操作、權限不足、狀態過期、操作到一半離開、人工覆寫及不可逆操作。清楚寫出使用者看到什麼、資料是否保存、能否重試及後續如何恢復。

### 8. 非功能條件

只列真正會影響方案或驗收的安全、隱私、效能、容量、可用性、相容性、無障礙、成本、法規或維運條件。能量化就量化；不能量化時標 owner，不寫「要快」「要穩」。

### 9. 驗收案例

以具體 Given／When／Then 覆蓋主流程、門檻、失敗與恢復。驗收結果必須可觀察，不用「正常」「正確」「適當」當預期結果。案例引用對應行為與規則 ID。

### 10. 開發切片與技術待辦

依可演示、可驗收的端到端行為切片，避免只拆成前端頁面、後端 API 或資料表。標示依賴與完成證據。

另列 `TECHNICAL_DESIGN` 問題交由 RD 決定，例如 API 形狀、schema、架構或鎖定策略；不得把仍會改變使用者結果的產品問題偽裝成技術待辦。

### 11. 決策與變更紀錄

只保留影響理解與後續維護的決策：選了什麼、否決什麼、理由、決策人、日期及受影響項目。需求變更時更新主體並記錄影響，不在文件尾端堆疊互相衝突的新舊說法。

## 寫作品質

- 先讓 RD 看懂整體工作，再進入欄位與例外。
- 使用一致的業務名詞；人名不是穩定識別碼。
- 一件事只在一處完整定義，其他位置使用連結或 ID。
- 用表格呈現真正需要比較的規則，不把長篇敘述塞進巨型儲存格。
- 清楚區分現況、正式需求、暫行方案、推論、技術建議與未決事項。
- 刪除探索噪音；保留會解釋「為什麼不能改」的決策理由。
- 對 RD 有用比章節齊全重要；不相關章節可標不適用或省略。

## 交付前的 RD 視角重讀

在宣稱完成前，只依 `rd-development-spec.md` 做一次 cold read：

1. 重述使用者主流程與最重要的三個分支。
2. 嘗試拆出第一批端到端任務。
3. 列出所有會造成兩種產品結果的疑問。
4. 檢查每個驗收案例是否能由文件中的規則唯一推出。

若第 3 項仍有內容，需求書只能是草稿；回到問答收斂，不得交給 RD 猜。
